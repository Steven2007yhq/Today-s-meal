# 商业化准备度审查

## 结论

项目已经跨过“概念稿”阶段，是一个可构建、可安装、交互完成度较高的 Windows 产品原型。菜谱检索、饭量换算、餐食日历、PDF、收藏降级、AI 网关、身份数据库和图片基础设施都有真实代码支撑。

目前仍不适合公开收费运营。综合代码证据，建议把当前状态定义为：

- 产品演示 / 投资人演示：可用，约 80% 准备度。
- 小范围非付费封测：基本可用，约 60% 准备度。
- 小范围真实付费试点：约 45% 准备度。
- 面向公众的商业发布：约 30% 准备度。

这里的百分比是工程准备度估算，不代表市场验证、营养学有效性或法律合规结论。

## 阻止收费上线的 P0 缺口

### 1. 交易基础闭环已完成，运营闭环仍欠缺

客户端直接修改 `isPro` 的演示路径已经移除。现有实现由服务端商品表定价，支持微信 Native / 支付宝预下单、响应验签、异步通知验签、商户和金额校验、支付事件幂等、订单状态查询、会员有效期续接与服务端权益读取。生产环境没有商户参数时不会开放付款，开发模拟通道也会被生产启动检查阻止。

仍缺真实商户联调、主动查单、关单、退款、补单、日终对账、异常订单后台、告警与客服处理流程；因此还不能把“代码闭环”等同于“可运营收款”。

上线标准：客户端永远不能自行开通权益；只能由服务端根据微信/支付宝已验签回调写入会员状态，再由权益接口返回。

### 2. 认证链路仍是开发级

- `/api/auth/send-code` 只创建验证码挑战并记录日志，未调用短信或邮件服务商。
- 滑块令牌由客户端随机生成，服务端只检查字符格式，不能防机器人。
- 微信/QQ 只生成授权 URL；没有回调、`state` 持久化校验、code 换 token、账号绑定或桌面深链回跳。
- 登录、AI 和公开接口缺少可横向扩展的限流、风控和滥用检测。

上线标准：接入真实短信/邮件、人机验证、OAuth 回调和 Redis/网关级限流；高风险操作需要审计记录。

### 3. 用户核心数据没有服务端闭环

餐食历史、日历修改、家庭档案和健康档案主要保存在本地。Pro 状态已经改由服务端权益表决定，但其他核心数据仍未与登录账号可靠绑定，也没有同步、冲突解决、导入导出或多设备恢复。

上线标准：实现带用户授权的 profile、meal plan、meal entry、report API；明确离线队列、版本号和冲突策略。

### 4. 周报和健康场景会造成错误预期

周报分数、营养趋势、成就、宏量营养数据及部分健康提示是静态展示。乐龄模式涉及疾病史和用药风险，但没有营养数据授权来源、规则验证、临床审校、敏感信息单独同意或风险升级流程。

上线标准：所有指标必须由真实记录计算并标注数据来源；健康相关能力需法务和专业人员审校，默认定位为生活教育建议，不能暗示诊疗。

### 5. 隐私与合规功能只停留在文案

缺少可点击的用户协议和隐私政策、敏感个人信息单独同意、撤回同意、账号注销、数据导出、数据删除、留存期限、字段级加密、第三方 SDK 清单、个人信息影响评估和未成年人规则。

上线标准：把合规要求实现为产品流程、API、后台任务和审计证据，而不只是 README 提示。

### 6. 发布与运维链路不完整

- 现有 1.0.4 安装包生成于 2026-08-05，早于 2026-08-09 的安全启动检查、迁移账本和错误兜底提交；已安装版本仍带旧迁移文件。
- 没有 Windows 代码签名、自动更新源、灰度发布、回滚、崩溃上报或版本兼容策略。
- 没有 CI、staging、结构化日志、指标、告警、备份演练、灾难恢复或运行手册。
- 打包配置会把服务端源码、迁移、Docker 文件和脚本全部带入桌面安装包，增加体积并混淆客户端/服务端交付边界。

上线标准：服务器和桌面端分开交付；签名安装包只包含客户端运行所需内容；建立 CI/CD、监控、备份与回滚。

### 本轮已完成

- 固定全部直接依赖版本，避免 `latest` 带来的不可控升级。
- 新增 Node 版本约束、`test` 与 `check` 质量命令。
- 将导航、顶部栏、模态框壳、餐食种子数据、日历规划和浏览器存储从巨型组件拆出。
- 浏览器存储读写在隐私模式、配额耗尽或 JSON 损坏时不再向上抛错。
- 新增 38 个自动化测试，覆盖 AI 品牌隔离、身份提示、认证纯函数、密码哈希、生产配置、日历规划、本地存储、支付响应验签和金额校验。
- 新增独立支付网关与账单服务，交易逻辑没有继续堆进客户端组件；数据库金额为唯一计费依据。
- 修复开发依赖中的已知高危漏洞；完整 `npm audit` 为 0。

### 仍需继续

- `src/App.jsx` 仍约 1,600+ 行，应按 Today、Calendar、Report、Library、Favorites、Assistant、Auth、Settings 拆分。
- `server/index.mjs` 仍约 970 行，应按 auth、AI、catalog、favorites、media 路由拆分，并使用可注入依赖的 `createApp()` 以便集成测试。
- `src/styles.css` 约 90 KB，多个规则挤在单行，应按页面/组件拆分并接入格式化与样式检查。
- API 客户端存在重复的超时、JSON 解析和错误转换逻辑，应收敛到统一请求层。
- 数据库的完整 `schema.sql` 与实际迁移覆盖范围不一致；生产只能以迁移为真相，并增加 schema 一致性检查。
- 收藏既支持匿名 owner key 又支持登录用户 ID，应明确账号合并和越权模型。

## 建议路线

### 阶段 A：可信封测（2–4 周）

1. 拆分前后端巨型文件，建立 CI：测试、构建、依赖审计、迁移检查。
2. 部署独立 staging 后端；桌面端使用明确的环境配置，不再默认连接本机服务。
3. 把餐食、档案、报告数据接入账号；完成数据导出与删除的最小闭环。
4. 接入真实验证码、人机验证；支付入口在商户参数未配置时保持禁用，并暂时隐藏未闭环的 OAuth 和静态周报入口。
5. 生成新版本号安装包，完成代码签名和基础崩溃上报。

### 阶段 B：真实付费试点（再 4–6 周）

1. 用一个已审核商户完成真实联调，并补齐主动查单、退款、补单、对账、告警和异常订单后台。
2. 为 AI 加入登录绑定、用户配额、成本仪表盘、限流、内容安全和审计。
3. 用真实餐食记录计算周报；建立营养数据来源和计算测试集。
4. 上线用户协议、隐私政策、单独同意、注销、删除、留存和客服工单。
5. 做 50–200 人付费试点，验证次日/七日留存、计划采用率、AI 单用户成本、退款率和支持负担。

### 阶段 C：公开商业发布（再 6–10 周）

1. 自动更新、灰度、回滚、监控告警、备份恢复演练全部跑通。
2. 补齐第二支付渠道、续费管理、发票/客服流程和异常订单处理。
3. 完成图片、菜谱和营养数据的授权台账；清除无法证明商业使用权的素材。
4. 对家庭、乐龄和健身建议做专业审校、风险分级和 A/B 验证。
5. 根据试点数据决定定价和免费额度，而不是直接沿用当前演示价。

在 2–3 名全职工程师、1 名兼职 QA/运维以及法务/营养顾问可及时参与的前提下，从当前代码到小范围真实付费试点大约需要 6–10 周；到相对稳妥的公众商业发布大约需要 3–6 个月。若支付、短信、资质、素材授权或专业审校需要从零采购，周期应相应增加。
